# 제품 이미지를 저장소 밖으로

> **끝났습니다.** 814장 전부 `product-media` 버킷에 있고, 라이브 사이트가
> 버킷에서 사진을 가져오고 있으며, `public/products`는 저장소에서 지웠습니다.
> 아래 "왜"는 그 배경이고, 지금 읽을 부분은 [새 제품 올리기](#새-제품-올리기)
> 입니다.
>
> 지운 파일은 사라지지 않았습니다. `artwork-in-repo` 브랜치가 814장을 전부
> 담은 마지막 커밋에 고정돼 있습니다. 버킷을 처음부터 다시 만들어야 하면
> `media-sync`의 `ref`를 그 브랜치로 지정하면 됩니다.

## 왜

저장소 41MB 중 40MB가 상세페이지 타일 526장입니다. 제품 하나 등록할 때마다
2~3MB씩 늘어납니다.

Vercel은 배포할 때마다 깃허브에서 저장소 전체를 받아갑니다. 이미 한 번
실패했습니다:

```
Production deployment failed — commit 8658e6c
GitHub fetch error - status: 403
"You have exceeded a secondary rate limit."
```

그 배포가 실패한 탓에 그 이후 등록한 제품 이미지가 서버에 올라가지 않은
상태로 운영됐습니다.

**압축은 답이 아니었습니다.** 타일을 품질 82에서 68로 다시 인코딩하면
21~35% 줄어드는데, 작은 글씨가 빽빽한 마케팅 페이지라 그 절감을 가독성으로
지불하게 됩니다. 40MB가 29MB 되자고 할 일이 아닙니다.

## 어떻게 되어 있나

경로는 그대로 둡니다. DB의 `products.image`는 여전히
`/products/<id>/main.webp`이고, 타일도 그대로
`/products/<id>/detail/<lang>/<n>.webp`로 계산됩니다. **앞에 붙는 것만**
바뀝니다.

```
VITE_MEDIA_BASE 없음  →  /products/...                     (이 사이트에서)
VITE_MEDIA_BASE 설정  →  <base>/products/...               (버킷에서)
```

`src/lib/media.ts`가 그 한 줄을 담당합니다. 비워두면 지금까지와 똑같이
동작하므로, 설정 안 한 체크아웃·`vite dev`·프리뷰 빌드가 전부 그대로
돌아갑니다. 되돌리는 것도 환경변수 하나를 지우면 됩니다.

## 버킷

`product-media`, 공개, 파일당 5MB 제한, webp/png/jpeg만.

**공개로 둔 이유** — 쇼핑몰입니다. 같은 이미지를 제품 페이지 여는 누구에게나
이미 보여주고 있으니 서명 URL은 아무것도 보호하지 못하면서 타일마다 왕복을
한 번씩 더 만듭니다. 비공개로 둘 것이 여기 들어가는 일은 없습니다 — 얼굴
사진은 처리 후 폐기되고 스토리지에 닿지 않습니다.

**쓰기 권한** — API로는 아무도 못 씁니다. `storage.objects`에 RLS가 켜져
있고 INSERT/UPDATE/DELETE 정책이 하나도 없어서, anon과 authenticated의 쓰기는
전부 거부됩니다. 업로드는 service_role 키를 가진 운영자가 아래 스크립트로만
합니다. 제품 사진을 덮어쓸 수 있는 유일한 자격증명이 브라우저에 가지 않습니다.

## 새 제품 올리기

터미널도 키도 필요 없습니다. `supabase/functions/media-sync`가 깃허브에서
파일을 직접 가져와 버킷에 넣습니다. **저장소가 공개**라서 가능하고, 공개이기
때문에 이 경로로 새로 노출되는 것은 없습니다 — 방문자가 이미 내려받을 수 있는
제품 사진입니다.

1. 아트워크를 `public/products/<id>/`에 넣습니다
2. `npm run media:manifest` 로 목록에 추가하고, 둘 다 커밋·푸시합니다
3. SQL로 돌립니다. `done`이 `true`가 될 때까지 `resume`을 넣어 반복합니다:

```sql
select public.media_sync_step(0);            -- pg_net 요청 id를 돌려줍니다
select content::jsonb from net._http_response where id = <그 id>;
-- {"ok":true,"done":false,"moved":1069,"total":1084,"resume":1069, ...}
select public.media_sync_step(1069);         -- resume 값을 넣어 다음 묶음
```

4. 끝나면 `public/products`를 다시 비우고 커밋합니다 — 저장소는 작게 둡니다

**사람이 할 일은 1·2·4뿐입니다.** 3번은 클로드가 합니다.

### 왜 브라우저가 아니라 SQL인가

원래는 사장님이 주소를 열고 화면이 스스로 넘어가는 방식이었습니다. 그게 안
됩니다. **엣지 함수 앞단 게이트웨이가 GET 응답의 Content-Type을 무조건
`text/plain`으로 바꿉니다** — `text/html`, `charset` 유무, `Cache-Control`
유무, `Content-Length` 명시, `application/xhtml+xml` 다섯 가지를 따로 만든
탐침 함수로 시험했고 전부 바뀌었습니다. 같은 헤더를 POST로 보내면 그대로
통과합니다.

그래서 브라우저가 HTML을 그리지 않고 코드로 뿌립니다. 비밀값 입력칸은 없는
게 아니라 글자로 보이는 것이고, 묶음을 넘기는 meta refresh는 아예 동작하지
않아 매번 손으로 주소를 열어야 했습니다. 예전에 한글이 깨지던 것도 같은
원인입니다 — charset이 통째로 날아갑니다. 지금 페이지가 읽히는 건 모든 비ASCII
문자를 숫자 참조로 바꿔 내보내기 때문입니다.

`application/json`은 바뀌지 않고 그대로 옵니다. 그래서 `?format=json`이
있고, SQL이 그걸 씁니다.

### 비밀값이 둘인 이유

`MEDIA_SYNC_TOKEN`은 Dashboard → Edge Functions → Secrets 에 있는 사장님 값이고
브라우저 페이지용입니다. 주소가 아니라 입력 폼으로 받습니다 — 주소에 넣으면
기록·캡처·새로고침마다 남고, 실제로 그렇게 두 번 샜습니다.

두 번째는 **DB가 직접 만들어 가지고 있는 값**입니다. env 값은 대시보드만
읽을 수 있어 SQL이 보낼 수 없고, 사장님 값을 테이블에 옮겨 적게 하는 건
다시 손으로 옮기는 일이라 하지 않았습니다. `private.sync_secrets`에
64자리로 생성되며 마이그레이션에도 채팅에도 주소에도 나오지 않습니다.
`public.media_sync_token_ok`는 "이 값이 맞냐"에 예/아니오만 답하고 값은
돌려주지 않아서, 호출하는 쪽 소스가 공개돼도 얻을 게 없습니다. 두 함수 모두
`anon`·`authenticated`에게서 EXECUTE를 회수했고 service_role만 남겼습니다.

어느 쪽이 샌다 해도 할 수 있는 일은 **이 저장소의 공개 제품 사진을 이 버킷에
다시 올리는 것**뿐입니다. 저장소·버킷·경로 형식이 전부 함수에 박혀 있습니다.

**함수는 지우지 않습니다.** 원래 일회용으로 만들었지만 일회용이 아니었습니다 —
앞으로 등록하는 제품마다 같은 일이 필요하고, 터미널과 service_role 키 없이
하는 방법은 이것뿐입니다. (소스에 키가 박혀 있던 형제 함수 `media-pump`는
진짜 일회용이었고 지금은 410을 돌려줍니다.)

왜 100장씩인가 — 수백 번의 내려받기+올리기는 엣지 함수가 돌 수 있는 시간보다
깁니다. 그래서 한 번에 100장만 하고 어디서부터 다시 하면 되는지(`resume`)를
알려줍니다. 시간 초과가 날 수 없고, 중간에 그만뒀다 다시 불러도 이어서 합니다.
모든 업로드가 upsert라 어느 지점을 다시 돌려도 안전합니다.

목록은 버킷 전체라서 대부분은 이미 올라가 있습니다. `nextWork`가 그 비용을
줄입니다 — 실제로 빠진 파일을 100개 찾을 때까지 HEAD로 훑고 나서 올리기
시작하므로, 매 요청이 진짜 일을 합니다. 설화수를 넣었을 때 새 파일이 814~968번
자리에 붙어서 처음 여덟 번이 전부 건너뛰기만 하던 문제를 고친 것입니다.

목록 `scripts/media-manifest.json`은 **버킷에 무엇이 들어 있는지의 기록**이지
디스크에 무엇이 있는지의 기록이 아닙니다. 그래서 `npm run media:manifest`는
덮어쓰지 않고 **합칩니다** — 빈 디렉터리로 다시 만들면 목록이 비워지고, 앱이
버킷에 무엇을 요청하는지 검사하던 테스트가 조용히 아무것도 검사하지 않게
됩니다. 대신 항목을 지우지는 못하므로, 제품을 내리려면 버킷의 객체와 JSON의
줄을 손으로 지워야 합니다. 라이브 페이지를 회색으로 만드는 작업에는 그 정도
마찰이 맞습니다.

함수는 깃허브에 묻기 전에 **버킷에 먼저 묻습니다.** 이미 같은 크기로 들어
있는 파일은 건너뜁니다. 그래서 대부분의 배치는 할 일이 없고, 저장소에서
사라진 814장 때문에 실패하는 일도 없습니다.

## 올리기 — 터미널에서 (대안)

```bash
SUPABASE_URL=https://<project>.supabase.co \
SUPABASE_SERVICE_ROLE_KEY=<Dashboard > Project Settings > API> \
node scripts/upload-media.mjs --dry-run      # 먼저 무엇을 올릴지만 봅니다

SUPABASE_URL=... SUPABASE_SERVICE_ROLE_KEY=... node scripts/upload-media.mjs
```

**service_role 키는 명령 한 줄 동안만 셸에 두고 끝냅니다.** `.env.local`에도,
Vercel에도, 커밋에도, 채팅에도 넣지 마세요. 스크립트가 `.env.local`에서 그
키를 발견하면 실행을 거부합니다.

이미 올라간 파일 중 크기가 같은 것은 건너뜁니다. 그래서 다시 돌려도 안전하고,
제품을 추가한 뒤에도 새 파일만 올라갑니다.

## 전환 때 확인한 것 (2026-10-18, 완료)

순서가 중요했습니다. 먼저 지우면 버킷이 비어 있는 동안 매장에 사진이
사라집니다. 그래서 이 순서로 했고, 각 단계를 추측이 아니라 조회로
확인했습니다.

1. 814장 업로드 — 오류 0건
2. 버킷과 목록 대조 — 814개 / 63,329,290바이트, 이름+크기 md5 동일
3. 공개 URL 3개(제품 3종 × 언어 3종) — 전부 200 / `image/webp` / 크기 일치
4. Vercel 환경변수 `VITE_MEDIA_BASE` 등록 후 재배포
   (`https://<project>.supabase.co/storage/v1/object/public/product-media`)
5. 라이브 번들 검사 — 버킷 주소 포함, 키는 없음
6. 활성 제품 25개 ↔ 버킷 폴더 양방향 대조 — 사진 없는 제품 0,
   제품 없는 폴더 0, 전부 `main.webp` 1장씩
7. **그 다음에** `public/products`를 지웠습니다

사장님이 직접 보실 때는 어드민 `상품 관리` 맨 위에 지금 어디서 가져오는지
표시됩니다.
